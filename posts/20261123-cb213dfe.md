# Hermes Agent kanban swarm 功能深度解析

想让三个 agent 并行调研、一个校验、一个汇总，你会怎么编排？用 `delegate_task` 起一棵子 agent 树看似够用：父进程原地阻塞等 join，笔记本一合盖、会话一压缩，审计记录和失败现场全丢。Hermes Agent 的解法是把编队落库——`hermes kanban swarm` 一条命令原子提交一张持久任务图，进程死了、机器重启了，swarm 照样接着跑。

## 一条命令，一张任务图

```bash
hermes kanban swarm "重构支付模块并补齐测试" \
  --worker backend:后端重构:code-review \
  --worker tester:测试补齐:test-driven-development \
  --verifier reviewer \
  --synthesizer tech-writer
```

这条命令会原子提交 Kanban Swarm v1 拓扑：一张已完成的 root/blackboard 卡（共享上下文就是挂在它上面的结构化 JSON comments），接着 N 张并行 worker 卡，一张等待全部 worker 的 verifier 卡，最后一张等 verifier 的 synthesizer 卡。原子提交意味着不会出现「图建了一半」的孤儿卡。**为什么重要**：多智能体最容易翻车的地方不是单个 agent 不够聪明，而是编排碎在半路——一次性提交把拓扑完整性变成了一个数据库事务问题。worker 卡还可以开 goal_mode：每轮结束由 judge 对照卡的验收标准判分，不达标就在同一会话续跑，上限默认 20 轮——「写完没有」从此是可判定的验收，而非 agent 的自我感觉。

## 断点续跑的秘密：状态外置

swarm 里的每张卡都是 `kanban.db`（SQLite/WAL）里的一行。dispatcher 默认内嵌在 gateway 里，每 60 秒一个 tick：回收 stale/crashed worker，promote 依赖就绪的卡，原子 claim，然后按 profile 身份 spawn 独立 OS 进程。状态机共 9 态（triage/todo/scheduled/ready/running/blocked/review/done/archived）；注意 `claimed` 不是状态，而是 `ready→running` 之间的原子动作加租约列。stale 检测留了余量：运行超 4 小时且 1 小时无 heartbeat 才 SIGTERM 回收，且回收不计失败。**为什么重要**：编排状态存在数据库而非某个进程的内存里，任务因此能跨重启、跨进程存活，存活时长从小时到天级，worker 还能长期挂 heartbeat 保活——这正是进程内 `delegate_task` 不具备的能力。

## 依赖边与质量闭环

父卡的 summary/metadata 会注入子卡的 worker_context，全部父卡 done 后子卡自动 `todo→ready`；评审走 `request_review` 进 review 列而非 block，`request_changes` 打回实现者、不计 unblock 循环；同卡连败 2 次（`DEFAULT_FAILURE_LIMIT=2`）自动 block 等人处理；同因反复 block→unblock 到第 2 次会触发 block_loop_detected、自动升级 triage 交人裁决；一卡 N 次尝试会记成 N 行 task_runs，SQLite 审计永不丢失。**为什么重要**：谁等谁、失败几次算放弃、什么时候必须叫人，这些规则全被编码成数据库状态机，而不是指望某个 agent 自觉。

## 对照：差的是持久性

`delegate_task` 是进程内 RPC（fork→join，父阻塞、失败即失败），cron 只有定时触发、没有任务图，tmux/PTY 直接 spawn 是有进程、无状态机；横向看 AutoGen、CrewAI、LangGraph，编排状态都在进程内。kanban 的差异点一句话：**状态外置 + worker 独立进程**。本机 blog 板实测 8 卡 5 条依赖边，从拆解、调研、撰写到审校整条链自动流转。

## 边界先说清

单机限定：crash 检测依赖本地 PID，docs 的「Out of scope」明确写了不支持多机，多机部署等于每机一板。**为什么重要**：选型时别把它当分布式队列用；在单机范围内，它已经把「多 agent 长任务可靠协作」这件事做扎实了。
